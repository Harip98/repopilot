# M4 Evaluation Harness Implementation Plan

> The plan as written before implementation, kept as design history; its checkboxes were not used for tracking. [README.md](../../README.md) and [architecture.md](../architecture.md) describe the system as built.

**Goal:** Measure the agent honestly across 25 reproducible tasks in three fixture repos, using the metrics the spec names.

A single command runs a split against a model. It records one row per task and writes a resumable report:
- `eval/reports/<name>.jsonl`, one line per task;
- `eval/reports/<name>.md`, a summary;
- `eval/reports/<name>.meta.json`, the model, git sha, task-set hash and budget.

**Architecture:**
- `repopilot.eval` drives M3's `prepare_bench_run → start_run(auto_approve) → grade → destroy` once per task, with no human in the loop.
- Each outcome is written to `eval_results` and appended to the JSONL file. A task already present for the eval name is skipped, so an interrupted eval resumes.
- Scoring is deterministic: no LLM judge. It uses Wilson 95% intervals for rates and nearest-rank p50/p95 for latency.

**Tech Stack:** M3 runner, psycopg, the existing bench format, and Ollama via its OpenAI-compatible endpoint. The development machine has no hosted-model key, so the evals use local models; a hosted model is a configuration change (`REPOPILOT_LLM_BASE_URL`, `REPOPILOT_LLM_MODEL`, `REPOPILOT_LLM_API_KEY`).

**Spec:** [docs/plan.md](../plan.md), sections Eval and M4 (the metrics list).

## Global Constraints

- **Per-task record (`EvalResult`).**
  - Identity: `eval_run`, `task_id`, `run_id`, `model`, `difficulty`, `split`.
  - Outcome: `status`, `failure_reason`, `resolved`, `patch_applied`, `visible_tests_passed`.
  - Counts: `retries`, `llm_calls`, `tool_calls`, `tool_failures`, `unauthorized_attempts`, `test_files_modified`.
  - Cost and time: `latency_ms`, `prompt_tokens`, `completion_tokens`, `cost_usd`.
  - Diagnostics: `heldout_exit_code`, `error`.
- **Definitions.**
  - `resolved`: the run ended `completed` (it passed harness validation) **and** the held-out tests pass on the final workspace.
  - `patch_applied`: the final diff is non-empty.
  - `visible_tests_passed`: the last validation passed.
  - `test_files_modified`: any changed path under `tests/` that already existed in the base workspace. New test files do not count.
  - A task that raises (model server down, sandbox error) is recorded with `status="error"` and the error text. It counts as unresolved and is reported separately.
- **Summary metrics.** The report table carries all of these:
  - resolution rate with its Wilson 95% CI;
  - patch-apply rate and visible-test pass rate;
  - tool-call failure rate (`Σ failures / Σ tool calls`) and average retries;
  - p50/p95 latency;
  - Σ tokens, and tokens and USD per resolved task;
  - Σ unauthorized attempts and the count of runs with `test_files_modified`;
  - a by-difficulty breakdown and a per-failure-reason count.
- **Evals run sequentially** by default (`--concurrency 1`), because the local GPU serves one model. The default budget is M3's.
- **Tasks.** There are 25 in total:
  - `orders-api`: 10 (existing)
  - `textkit`: 8 (new pure-Python text utilities)
  - `inventory`: 7 (new FIFO stock ledger with reorder logic)

  Each repo's tasks are made by a generator script like `bench/generate_orders_api_tasks.py`, and must pass `repopilot bench validate`. Splits: `dev` has 15 tasks and `test` has 10 (4 orders-api, 3 textkit, 3 inventory).
- **Freezing the test split.** `bench/test_split.sha256` holds the sha256 over the sorted test-split task directories' file contents. `repopilot eval run --split test` refuses to run if it differs, unless `--allow-unfrozen` is given. `bench/FREEZE_LOG.md` records each freeze.
- **Prompt fixes from the M3 smoke run.**
  - The system prompt states that paths are relative to the repository root and never prefixed with the repo name.
  - `intake` adds a depth-2 file listing (from `find`, excluding `.git`) to the issue message.
- **README results.** The README gets a results table copied verbatim from the generated `.md`. It names the model, hardware and date, and lists the limitations:
  - visible tests pass on every buggy base;
  - the tasks are small, single-file fixes;
  - the models are local.

## Review Focus

1. **The eval is killed halfway.** Rerunning the same `--name` skips finished tasks and appends only the rest; the summary covers all tasks once. Test: `test_eval_resumes` (Task 2).
2. **A task errors.** For example the Ollama server stops, or sandbox creation fails. The eval records `status=error`, destroys the sandbox if one was made, and continues with the next task. Test: `test_task_error_recorded_and_continues` (Task 2).
3. **Wilson CI and percentiles at the edges:** n=0, all resolved, none resolved, n=1. No division by zero, and the bounds stay within [0, 1]. Test: `test_score_edges` (Task 1).
4. **The agent edits an existing visible test.** `test_files_modified` is true, and the run is still graded on held-out tests. Test: `test_test_files_modified_flag` (Task 2).
5. **The test split is changed after freezing.** `eval run --split test` refuses, and the message names the changed tasks. Test: `test_frozen_split_guard` (Task 4).
